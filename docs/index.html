超时之后，
别把同一件事做两遍

为什么重试会导致重复操作？关键不在“再发一次”，而在于让服务端认出：这是同一件事的重试，还是一件新的事。

完全虚构的工程情境

“纸舟归档服务”、接口、键与任务编号均为教学示意，不对应真实产品或事故。

这里只解释机制，不声称实测收益。

先纠正一个直觉

超时描述的是你还不知道结果，
不是服务端的“撤销键”。再发送，不等于该再执行。

01 / 区分业务意图

键跟着“这件事”，不跟着“这次发送”。

非天然幂等的创建操作，如果每次到达都被当成新操作，就可能产生重复任务。幂等键用来把多次发送归回同一个业务意图。

同一件事 · 重试

“刚才那份归档，做好了吗？”

首次提交前保存 K-A 与参数。结果未知时，复用原键、原参数；有效记录已完成，就返回原结果。

若原操作仍在处理中：按接口约定等待、查询或退避重试，不要启动第二份工作。

另一件事 · 新操作

“我明确还要再创建一份。”

只有新业务意图才使用新键 K-B。参数相同也可以是不同操作，不能只靠参数相同合并请求。

不要因为超时就换键。新键可能创建另一任务；业务唯一约束若另行拦截，那是另一层保证。

02 / 服务端如何判断

认得键，也要核对参数和状态。

先验证身份、权限与参数，再在约定作用域内查找记录。键不是访问凭证；同键不同参数必须拒绝，不能覆盖原记录或悄悄重做。

请求到达后的处理规则 · 以服务端契约为准
记录情况参数处理方式
无有效记录请求合法原子占用键，再执行。不能“查到没有”就直接开工。
处理中一致返回可识别的处理中状态，或按约定等待；不重复执行。
已完成一致返回已保存的业务结果或稳定引用。
有效记录存在不一致拒绝参数冲突；不覆盖、不复用错误结果、不执行新操作。
已过期或清理无法确认原保证不再成立。先核对业务状态，再走约定恢复路径。

03 / 保证有边界

一个请求头，不等于“永远只执行一次”。

幂等保证依赖服务端记录、原子性和保留期。客户端带上键，只是协议的开始。

I

并发时，
只能有一个执行者

两个请求可能同时查到“没有记录”。要用唯一约束、事务或等效原子占用来竞争同一有效键；普通的“先查后写”不足以去重。

II

业务与记录，
不能各自成功

防止“业务已提交，结果记录却没写入”的崩溃窗口。本例可将任务创建与完成记录放进同一事务。涉及跨系统副作用时，还需下游幂等、事务消息或对账等机制；本地事务、锁或缓存不自动覆盖远端动作。

III

记录到期，
保证也可能到期

保留期要与重试窗口协调。记录过期、丢失或清理后，同键也可能被当作新请求。此时应用业务标识查询或走对账恢复，不能盲目重试或换键，更不能承诺永久去重或跨系统无条件 exactly-once。

带走这条判断规则

重试重复的是发送，
不应该重复业务意图。

失败、回滚及可重试错误如何记录、何时允许重新执行，都需由接口契约规定。不能把所有失败都解释为“从未执行”。

退避减少请求压力，但退避本身不提供去重保证。

  1. 首次提交前，保存幂等键及对应参数。
  2. 遇到超时，先理解为“结果未知”。
  3. 在约定窗口内，同一操作复用原键原参数；按契约查询或退避重试。
  4. 只有明确的新业务意图，才生成新键。
  5. 超过保留期，先核对业务状态，再恢复。

从复杂回答到阅读页面　原始问题与完整回答保存在 examples/reading-map.input.md；视觉正文为 examples/reading-map.fragment.html。页面依次展开请求关系、业务意图对照、处理规则与保证边界，而不是把长文切成小卡片。

构建方式　由 VibeView 1.5.2 发布版的 scripts/compose.py 组装，内嵌 assets/design.css。组装器接收 HTML 片段，不解析 Markdown。以下命令在项目根目录执行；要求 docs 已存在且目标文件尚不存在。

python3 -B scripts/compose.py examples/reading-map.fragment.html docs/index.html --title '超时之后，别把同一件事做两遍' --theme violet
