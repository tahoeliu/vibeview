Retry the request.
Reuse the result.

The server may finish the work before the client times out. An idempotency key lets a retry find the original operation instead of starting a second one, within the API’s documented retry window.

One operation, one key.

Reuse the original key and parameters while the record is valid.

Use a new key when you intend to start a new operation.

The key distinction

A timeout means the result is unknown.
The work may already be done.

01 / Identify the operation

Give each operation a key. Keep it for retries.

Creating a task twice can produce two tasks. An idempotency key gives the server a way to recognize repeated attempts to perform the same operation.

Same operation · Retry

“What happened to my archive request?”

Save K-A and the request parameters before sending the first request. When the result is unknown, reuse the original key and parameters; if the valid record is complete, return its result.

If the original operation is still in progress: wait, query, or retry with backoff as the API specifies; do not start a second operation.

A separate operation

“Create a second archive.”

A new operation gets a new key K-B. Two intentional operations can have identical parameters; do not merge requests based only on matching parameters.

Do not change the key because of a timeout. A new key may create another task. A separate business uniqueness constraint would be a different layer of protection.

02 / How the server decides

Check the key, the parameters, and the record.

Authenticate the caller, check permissions, and validate the request before looking up the key in its defined scope. The key does not grant access. If the parameters differ from the stored request, reject the conflict.

K-A is a placeholder. Real keys must be sufficiently unique within their scope. The API contract must define how parameters are normalized and compared.

The operation’s result is reused. Response headers and other transport details do not have to be byte-for-byte identical.

03 / Know the limits

The key is only part of the guarantee.

Safe retries depend on durable records, atomic operations, and a defined retention period. Sending a key is only the client’s part of the protocol.

I

Claim the key
atomically

Two requests can both observe “no record.” Use a unique constraint, transaction, or equivalent atomic claim to compete for the same valid key; an ordinary “check then write” is not enough to deduplicate.

II

Keep the work
and record in sync

Prevent the crash window where “the operation committed but the result record was not written.” Here, task creation and its completion record can share one transaction. Cross-system side effects need mechanisms such as downstream idempotency, transactional messaging, or reconciliation; a local transaction, lock, or cache does not automatically cover remote actions.

III

Respect the
retention window

Coordinate the retention period with the retry window. After a record expires, is lost, or is deleted, the same key may be treated as a new request. Query by a business identifier or use reconciliation and recovery; do not blindly retry or change keys, and do not promise permanent deduplication or unconditional exactly-once behavior across systems.

Put it into practice

One operation.
The same key for every retry.

The API contract must specify how failures, rollbacks, and retryable errors are recorded and when re-execution is allowed. Do not interpret every failure as “never executed.”

Backoff reduces request pressure, but backoff itself does not provide deduplication.

  1. Before sending the first request, save the key and parameters.
  2. On timeout, treat the result as “unknown.”
  3. Within the defined window, reuse the original key and parameters for the same operation; query or retry with backoff as specified.
  4. Use a new key only when intentionally starting a new operation.
  5. After the record expires, check what happened before attempting recovery.
